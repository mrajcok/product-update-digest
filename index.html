How to Implement Full-Stack Observability | Cribl

Full-stack observability enables comprehensive system understanding by examining telemetry across all layers – applications, infrastructure, and user experience.

  • The guide recommends a nine-step process, starting with assessing the current state and defining measurable outcomes (SLOs/SLIs) before instrumenting systems.
  • OpenTelemetry (OTel) is presented as a key technology for consistent instrumentation, offering vendor-neutral APIs and the OpenTelemetry Protocol (OTLP) for logs, metrics, and traces.
  • A telemetry pipeline is crucial for unifying data – collecting, normalizing, enriching, filtering, and routing it to various destinations – decoupling collection from analysis.
  • Cost optimization is emphasized through techniques like data tiering, reduction before storage, and tracking costs by team/service, along with governing access and securing sensitive data.

OcientAIQ Unified Data Platform Release Notes — 28.0

  • Ocient has released the Ocient Management UI, a web-based interface for system health monitoring, query activity, data ingestion, storage, node status, an interactive SQL Console, and a Pipeline Builder.
  • Data Pipeline loading now includes accurate metrics for ingest, fan-out, and filtering; pipelines can be quiesced with QUIESCE, and restarted at a specific file offset with ALTER PIPELINE.
  • The Ocient MCP Server (ocientmcp Python package) is now available, enabling AI agents and code editors to interact with Ocient systems via the Model Context Protocol (MCP).
  • Data Flows have been added, allowing sequential execution of multiple SQL statements with support for variables, loops, conditional branching, and error handling.
  • New SQL syntax features include FETCH FIRST/FETCH NEXT, the ROW() constructor (alias for tuple()), hexadecimal/octal/binary integer literals, underscore digit separators, and WITH RECURSIVE for recursive CTEs.
  • Data Pipeline metrics have been enhanced to show throughput details (including fan-out) with new views for rows and bytes processed; ALTER PIPELINE SQL is enhanced to update pipeline configurations in place.
  • Kerberos authentication is now supported for loading data from HDFS sources, along with Parquet data loading from HDFS.
  • New array functions have been added: ARRAY_INTERSECT_DISTINCT_COUNT, ARRAY_TRANSFORM_WITH_ORD, JACCARD_SIMILARITY, and ZIP_WITH_ORD.
  • Workload management now includes GRANT and REVOKE support for USE and VIEW privileges on service classes.
  • Machine learning model updates include the UNDERSAMPLING model, expanded training metrics (accuracy, confusion matrix, R², RMSE, etc.), the ROOT_MEAN_SQUARED_ERROR aggregate function, standardized model options, and new predict and predict_probabilities meta functions.
  • DDL statements have been extended with ALTER TABLE SET COMMENT, GET NODE TOKEN/REVOKE NODE TOKEN, and new parameters for CREATE/ALTER CONNECTIVITY_POOL (related to SSO and OpenAPI settings).
  • New scalar functions MAP_PUT, MAP_GET, and MAP_DELETE provide map functionality within SQL.
  • The HTTP Query API now correctly terminates queries exceeding service class limits, resolving a previous indefinite FINALIZING state issue.
  • Several new system catalog tables (sys.mcp_tools, sys.pipeline_metrics_current, sys.pipeline_metrics_historical) and column additions have been implemented for improved monitoring and reporting.
  • Data Pipelines are now the preferred method for loading data; the LAT functionality is deprecated and will be removed in a future release.
Ocient blog · 2026-10-07

The Modal Tax: Rethinking the best-of-breed stack

OcientAIQ™ Unified Data Platform addresses performance and cost issues arising from “agentic analytics” – AI agents composing queries across multiple data systems.

  • Agentic analytics creates a “modal tax” due to the repeated crossing of boundaries between different data systems, incurring costs in tokens, accuracy, and latency.
  • OcientAIQ™ aims to eliminate this tax by providing a single engine to natively handle relational, geospatial, ML (via OcientML™), graph, vector search, and real-time analytics over one data copy.
  • The platform utilizes Compute Adjacent Storage Architecture™ (CASA) and in-cluster loading to reduce latency and enable immediate querying of streaming data, keeping all operations within a unified query plan.
  • OcientAIQ™ offers fixed, capacity-based pricing to encourage exploratory agent behavior without per-action metering, supporting continuous iteration and materialization of intermediate results.
Ocient blog · 2026-10-07

CASA: Where your data sits matters more than ever in the age of AI agents

  • Ocient introduced Compute Adjacent Storage Architecture (CASA) designed to address performance bottlenecks caused by network latency when AI agents issue numerous queries against large historical datasets.
  • CASA keeps storage (NVMe SSDs) physically close to compute nodes via PCIe connections, delivering roughly one-fifteenth the latency of decoupled compute and storage approaches.
  • Ocient AIQ utilizes a tunable erasure coding scheme for data reliability, requiring roughly 1.2 PB of storage to protect 1 PB of data against two node failures, compared to 3 PB for 3x replication.
  • CASA’s co-location of compute and storage allows for consistent performance regardless of deployment location (public cloud, private cloud, on-premises, or air-gapped facility).

The Modal Tax: rethinking the best-of-breed stack

OcientAIQ™ is a unified data platform designed to address the performance and cost challenges introduced by agentic analytics workflows.

  • Agentic analytics creates a “modal tax” due to the cost of frequent data transfers between best-of-breed systems – specifically, a token tax (context window costs), an accuracy tax (loss of information across systems), and a latency tax (serialization/deserialization overhead).

  • The platform utilizes Compute Adjacent Storage Architecture™ (CASA) on local NVMe to serve both reads and writes efficiently, eliminating data movement and associated costs.
  • OcientAIQ’s pricing is fixed (per-core, capacity-based), removing cost friction for exploratory agentic workloads and enabling iterative data analysis without usage-based metering.

Inside the Ocient Engine: Casting, timestamps, and names

Ocient provides flexible SQL syntax for casting and timestamp handling, drawing inspiration from both Postgres and DB2 while introducing unique features.

  • Ocient supports multiple ways to retrieve the current timestamp, including now(), current_timestamp, and special registers, all mapping to the same internal function with appended suffixes to resolve naming collisions.
  • Casting can be achieved using ANSI SQL, Postgres' :: syntax, explicit CAST functions, or by using the data type name as a function (e.g., CHAR()).
  • Intervals are internally represented as integer or bigint values with assigned units, meaning INTERVAL is not a distinct data type and CAST(... AS INTERVAL) is not supported; date math is performed using constructors.
  • Timestamp components can be extracted using standard EXTRACT and date_part functions (returning doubles) or Ocient's shorthand functions like year() and minute() (returning integers/bigints), with subtraction resulting in nanosecond (bigint) or day (int) values.

Inside OcientAIQ™: Dataflows are the stored procedures you never have to create

Dataflows in OcientAIQ bring imperative programming capabilities—loops, variables, conditionals, and exception handling—directly to SQL, allowing complex processing within the database without creating stored procedures.

  • Dataflows are anonymous, ad-hoc SQL scripts submitted like queries, eliminating the need for pre-defined stored procedures or specialized protocols.
  • They support variables with strong typing and three expansion modes (@ for values, @@ for identifiers, and @! for raw text) for dynamic SQL generation.
  • Control flow constructs like WHILE loops, FOR loops, IF/ELSEIF statements, and TRY/EXCEPTION/FINALLY blocks are now available within SQL.
  • The platform optimizes execution by dynamically adjusting query plans between loop iterations and managing temporary data (scratch tables) automatically, with automatic cleanup upon completion or cancellation.

Inside the Ocient Engine: A deep dive into tuples

Ocient’s tuple data type functions as an anonymous struct, enabling powerful querying techniques.

  • Tuples are defined using doubled angle brackets (<<...>>) to specify inner types, similar to C++ templates or Java generics, and accessed by position starting with 1.
  • Ocient stores tuples as either virtual columns (separate columns logically related) or materialized (single binary blob), with tuples inside arrays always being materialized.
  • Tuple comparisons are performed lexicographically, meaning elements are compared in order, enabling specific sorting behavior (e.g., (1, "Z") comes before (2, "A")).
  • A "Tuple Max" trick can be used for point-in-time queries by packaging a timestamp and value in a tuple and utilizing the MAX() function's lexicographical sorting to efficiently retrieve the latest value, avoiding self-joins.

Graph analytics at scale without Spark bottlenecks

OcientAIQ™ introduces OCGraph, a library for running large-scale graph algorithms directly within the platform, avoiding Spark bottlenecks.

  • OCGraph is available in Java (via the Ocient JDBC driver - com.ocient:ocient-jdbc4) and Python (ocient-graph via PyPI). Both libraries offer identical algorithms and semantics.
  • Graphs are represented as two relational tables: a vertices table (with id as a primary key) and an edges table (with srcid and destid defining relationships). This leverages existing Ocient table features like indexing and querying.
  • The library provides algorithms including Connected Components, PageRank, Triangle Count, Weighted Shortest Paths, and Label Propagation, mirroring functionalities found in GraphX and GraphFrames but without the associated complexity.
  • Benchmarking against the LDBC Graphalytics dataset shows OCGraph performing 7x - 17x faster than Spark for iterative algorithms, and successfully completing Triangle Count where Spark failed due to memory limitations.
